Seed rows now use the real stations (1029TH Bourton Dickler / River Dikler / Bourton-on-the-Water, 2067 Swindon / Smestow Brook, 4009 Colwick / River Trent); town left NULL where unsure.
Tools/approach: Claude Code (Sonnet 5.5). Postman collection generated by a throwaway Python script (not committed), then replayed with a second throwaway script because Postman/newman is not installed here.
Decision & why (trade-off):
- Expected client errors are thrown as `ApiException` and caught in `Router::dispatch`, so controllers stay short. Anything else (PDO errors) still reaches the global handler and becomes a generic 500.
- PUT merges the supplied fields over the stored record, then validates the merged result. This lets `{"is_done":true}` work as a checkbox toggle, but it is not a strict full-replace PUT. `{}` on PUT is a valid no-op.
- Invalid id format (0, "abc") returns 422 with `fields.id`; a well-formed but unknown id returns 404. Chosen so "validation errors are always 422".
- Unknown JSON fields are silently ignored (consistent in both controllers).
- Wrong Content-Type returns 415; empty/malformed/non-object body returns 400; body over 64 KB returns 413.
Problem & fix: Port 8000 was already in use (an earlier dev server was running), so my own server did not start. Verified against the running one instead, since PHP reads files on every request. No code bugs found in testing.

## 2026-11-04, Phase 3
Worked on: EA integration (backend only). New `Services/EaClient.php` (cURL, typed result), `Services/EaCache.php` (file cache), `Services/EaNormaliser.php` (defensive parsing), `Controllers/StationController.php`, `Controllers/OverviewController.php`, routes in `public/index.php`, 17 new Postman requests (folder "3 EA integration"), `tools/nuwebspace-check.php`.
Tools/approach: Claude Code (Sonnet 5.5). Fetched the real EA responses with curl first (stations search, `/id/stations/4009`, `/id/stations/1029TH`, `/readings?latest`, and the `/doc/reference` page) and wrote the parsing from those.
Real shapes found (differ from assumptions): `items` is an OBJECT on a station detail but a list on searches/readings; `measures` is a single object on station 4009 but a list on 1029TH (2 measures: "Downstream Stage" and "Stage"); in station LISTS a measure has no `latestReading`/`unit`, only `unitName`, and `stageScale` is just a URL string (the detail endpoint has the real object with `typicalRangeLow/High`); an unknown station returns an HTML 404 page, not JSON; the documented trend endpoint is `/id/measures/{id}/readings?_sorted&_limit=96` (per measure; the station-level one mixes measures). Trend is NOT implemented yet (not in the Phase 3 deliverables); to add in Phase 5 if wanted.
Decision & why (trade-off):
- EA station search is CASE-SENSITIVE (`search=colwick` returns nothing, `Colwick` works; every word must start with a capital). The client title-cases a search term only when it was typed all-lowercase, so "colwick" works but "OBH" is left alone. Not perfect (e.g. "bourton-on-the-water") but avoids a second EA request.
- Latest readings are taken from the `latestReading` embedded in the station detail, instead of a second `/readings?latest` call (same data, one less request and one less failure point).
- Typical range is attached only to the "Stage" level measure, because `stageScale` belongs to the stage gauge; "Downstream Stage" gets `null` rather than a misleading range.
- Added a 5th typed status `not_found` (EA 404) next to ok/empty/unavailable/timeout so controllers can return 404. In `/overview` it is reported as `external.status = "empty"`.
- `/overview` is a separate `OverviewController` so `LocationController` (Phase 2) is unchanged. `config()` was split out of `db()`; behaviour is the same.
- Failure simulation without editing config: env vars `RIVERREADY_EA_BASE_URL`, `RIVERREADY_EA_TIMEOUT`, `RIVERREADY_EA_CONNECT_TIMEOUT` override the config values (used for the Postman failure cases on ports 8011 and 8012).
- Cache: 5 min, one file per URL in `ea.cache_dir` (default system temp dir), written via temp file + rename. Failures and 404s are never cached.
Problem & fix: First run returned 500 for every EA call: `curl_close()` is deprecated in PHP 8.5 and the project's error handler turns warnings into exceptions. Fixed by removing `curl_close` (a no-op since PHP 8.0). Found by reading the server log, not by the AI predicting it. Also: the first local run of `nuwebspace-check.php` hit a DNS timeout and the second run succeeded, so a single failure is not conclusive on the real server.

## 2026-11-04, Phase 5
Worked on: Actions UI (`ActionList`, `ActionItem`, `ActionForm`, `ProgressBar`, `hooks/useActions.js`, `constants/actionTemplates.js`), status chip + sparkline (`lib/status.js`, `StatusChip`, `Sparkline`, `TrendPanel`, `ReadingPanel` updated), Home cards (`LocationCard`), plain CSS appended to `components.css`. One backend addition: `GET /api/measures/{id}/readings?hours=24` (`EaClient::readings`, `EaNormaliser::readings`, `StationController::readings`, route, 3 Postman requests in folder 3).
Tools/approach: Claude Code (Sonnet 5.5) with the frontend-design skill; CLAUDE.md said no elaborate identity so existing tokens were kept. Checked the real EA readings endpoint with curl before writing the backend part.
Decision & why (trade-off):
- Trend endpoint did not exist, so the one allowed backend addition was made. Uses `/id/measures/{id}/readings?since=<now-24h>&_sorted&_limit=100` (a 24h window gives ~96 rows), cached 5 min by the existing EaCache. Points are returned oldest first. A valid-looking id EA does not know returns 200 with `items: []` (EA returns an empty list, not 404), so the UI says "Not enough recent readings".
- Status: value vs EA typical range gives High / Normal / Low; no range gives "Reading only"; no reading gives "No data". Each has icon + text. Stale threshold stays 6h. Typical range exists only for the "Stage" measure (Phase 3 decision), so other measures show "Reading only".
- Trend: mean of last 3 vs first 3 points; changes smaller than max(0.02, 3% of mean) count as steady. The thresholds are my own heuristic, not an EA rule, and flow measures use the same numbers.
- Templates: 10 generic items, added one POST at a time (no bulk endpoint, so no backend change); titles already in the list are skipped. Partial failure reports "Added N of M".
- Home: one `/stations/{ref}` request per card, no polling; relies on the backend cache. This is still N requests for N locations (accepted for a small list; a batch endpoint would be the fix if it grew).
- Sparkline code lives in a lazy chunk (`TrendPanel`) fetched only on the detail page.
Problem & fix: First EA test used a wrong measure id (`mASL`) and got an empty list; the real id comes from the station's measures (`mASD`). Also, EA returns 200 + empty items for unknown measures, so there is no 404 for them.
