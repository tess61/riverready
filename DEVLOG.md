## 2026-11-04, Phase 2
Worked on: Backend CRUD for locations and actions. `LocationRepository`, `ActionRepository` (prepared statements only), `LocationController`, `ActionController`, new `Http/Request.php` (id + JSON body helpers) and `Http/ApiException.php`, a `Validator::boolean` rule, routes in `public/index.php`, Postman collection (51 requests) in `backend/postman/`. Seed rows now use the real stations (1029TH Bourton Dickler / River Dikler / Bourton-on-the-Water, 2067 Swindon / Smestow Brook, 4009 Colwick / River Trent); town left NULL where unsure.
Tools/approach: Claude Code (Sonnet 5.5). Postman collection generated by a throwaway Python script (not committed), then replayed with a second throwaway script because Postman/newman is not installed here.
Decision & why (trade-off):
- Expected client errors are thrown as `ApiException` and caught in `Router::dispatch`, so controllers stay short. Anything else (PDO errors) still reaches the global handler and becomes a generic 500.
- PUT merges the supplied fields over the stored record, then validates the merged result. This lets `{"is_done":true}` work as a checkbox toggle, but it is not a strict full-replace PUT. `{}` on PUT is a valid no-op.
- Invalid id format (0, "abc") returns 422 with `fields.id`; a well-formed but unknown id returns 404. Chosen so "validation errors are always 422".
- Unknown JSON fields are silently ignored (consistent in both controllers).
- Wrong Content-Type returns 415; empty/malformed/non-object body returns 400; body over 64 KB returns 413.
Problem & fix: Port 8000 was already in use (an earlier dev server was running), so my own server did not start. Verified against the running one instead, since PHP reads files on every request. No code bugs found in testing.
